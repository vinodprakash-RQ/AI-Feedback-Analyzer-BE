# Feedback Management API Contract

This document describes the backend endpoints currently exposed by the Feedback Management system. The API is UI-independent and can be consumed by the separate dashboard frontend or by third-party applications.

## Base URL

For local development, use:

```text
http://localhost:5000
```

For another deployment, replace the host with that environment's API URL. Never commit real API secrets to this document; use the placeholders below.

All examples below are relative to that host.

## Endpoint Summary

| Method | Endpoint | Purpose | Authentication |
| --- | --- | --- | --- |
| `POST` | `/api/v1/feedback` | Accept third-party feedback asynchronously | API key required |
| `GET` | `/api/issues` | List and filter issues | Dashboard API key required |
| `GET` | `/api/issues/:id` | Retrieve issue details | Dashboard API key required |
| `PATCH` | `/api/issues/:id` | Update issue workflow status | Dashboard API key required |
| `GET` | `/api/feedback` | Deprecated read-only alias for issue listing | Dashboard API key required |
| `GET` | `/api/feedback/:id` | Deprecated read-only alias for issue details | Dashboard API key required |
| `GET` | `/api/dashboard/summary` | Deprecated endpoint; dashboard summary is not part of this module | Not applicable |

## 1. Submit Feedback

### `POST /api/v1/feedback`

Accepts feedback from an external product and immediately acknowledges receipt. AI classification is performed asynchronously and is not included in the acknowledgement response.

### Authentication

Provide either of the following headers:

```http
x-api-key: <third-party-api-key>
```

or:

```http
Authorization: Bearer <third-party-api-key>
```

Configure the local environment with secret placeholders:

```env
FEEDBACK_API_KEYS="<FEEDBACK_API_KEY>"
DASHBOARD_API_KEYS="<DASHBOARD_API_KEY>=*"
```

Use the feedback key only for `POST /api/v1/feedback`:

```http
x-api-key: <FEEDBACK_API_KEY>
```

Use the dashboard key for `/api/issues` and issue status updates:

```http
x-api-key: <DASHBOARD_API_KEY>
```

`DASHBOARD_API_KEYS` uses `key=project_id_1|project_id_2` entries. The `*` grants access to all projects. Send only the key portion in the request header, not the project permission suffix.

### Request headers

| Header | Required | Description |
| --- | --- | --- |
| `Content-Type` | Yes | Must be `application/json` |
| `x-api-key` or `Authorization` | Yes | Third-party API key |
| `Idempotency-Key` | No | Client-generated key to safely retry the same submission. Maximum 255 characters. |
| `X-Request-ID` | No | Client correlation ID. If omitted, the API generates one. |

### Request body

```json
{
  "message": "The application generated by AI is failing to build.",
  "user_id": "user_123",
  "conversation_id": "conv_456",
  "project_id": "project_789",
  "source": "ai-builder",
  "page_url": "/projects/123",
  "user_agent": "Mozilla/5.0",
  "metadata": {
    "request_id": "req_123",
    "environment": "production"
  }
}
```

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `message` | string | Yes | 1–20,000 characters; whitespace-only values are rejected. The stored value is preserved unchanged. |
| `user_id` | string | No | Maximum 500 characters |
| `conversation_id` | string | No | Maximum 500 characters |
| `project_id` | string | No | Maximum 500 characters |
| `source` | string | No | Maximum 120 characters |
| `page_url` | string | No | Relative path beginning with `/` or a valid absolute URL; maximum 2,048 characters |
| `user_agent` | string | No | Maximum 1,000 characters |
| `metadata` | object | No | JSON object serialized size must not exceed 10,000 bytes |

### Success response

**Status:** `202 Accepted`

```json
{
  "feedback_id": "fb_12345",
  "status": "received",
  "created_at": "2026-08-13T10:30:00.000Z"
}
```

Response headers include:

```http
X-Request-ID: 8f1a0d9e-...
X-RateLimit-Remaining: 59
```

The original feedback is stored in `FeedbackSubmission`. AI-generated values are stored separately in `FeedbackAnalysis` so the submission can be reprocessed later with another model or prompt.

### Idempotency behavior

When the same API client sends the same `Idempotency-Key` again, the API returns the original `feedback_id` and `created_at` instead of creating a duplicate submission. Idempotency keys are scoped per API client.

### Error response format

Errors from this versioned endpoint use the following structure:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Request body failed validation",
    "request_id": "8f1a0d9e-..."
  }
}
```

### Status codes

| Status | Code | Meaning |
| --- | --- | --- |
| `202` | — | Feedback accepted for asynchronous processing |
| `400` | `invalid_json` | Request body is not valid JSON |
| `401` | `invalid_api_key` | API key is missing or invalid |
| `422` | `validation_failed` | Request body violates the contract |
| `429` | `rate_limit_exceeded` | Client exceeded the rate limit; inspect `Retry-After` |
| `500` | `feedback_not_received` | The submission could not be persisted |
| `503` | `api_not_configured` | API key authentication is not configured on the server |

### Rate limiting

The current implementation allows 60 requests per API client per 60-second window. When the limit is exceeded, the response includes:

```http
Retry-After: 42
X-RateLimit-Remaining: 0
```

The current limiter is process-local. A shared Redis or equivalent implementation is required for consistent limits across multiple instances.

### Asynchronous analysis fields

The background analysis determines and stores:

- `sentiment`
- `intent`
- `category`
- `subcategory`
- `severity`
- `summary`
- `confidence`
- `model`
- `promptVersion`

The worker performs at most 10 Gemini analysis attempts per UTC calendar day. Additional submissions remain persisted with pending analysis and are processed by later scheduled worker runs. Each Gemini attempt, including a retry, consumes one of the 10 daily slots.

These internal processing fields are intentionally not returned to the third-party caller by the submission endpoint.

## 2. List Issues

### `GET /api/issues`

Returns a paginated list of persisted issues. Dashboard authentication is required. Project-scoped dashboard keys can only retrieve their permitted projects.

### Query parameters

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `category` | enum | No | — | `APPLICATION_GENERATION`, `AI_RESPONSE`, `BUILD_FAILURE`, `UI_UX`, `AUTHENTICATION`, `PERFORMANCE`, `INTEGRATION`, `PRODUCT_UI`, `FEATURE_REQUEST`, `PAYMENTS`, `CUSTOMER_SUPPORT`, `BUG_MOBILE`, `USABILITY`, `NOTIFICATIONS`, `ONBOARDING`, `SECURITY`, `AVAILABILITY`, `GENERAL`, `OTHER` |
| `subcategory` | string | No | — | Case-insensitive exact sub-category match |
| `sentiment` | enum | No | — | `POSITIVE`, `NEUTRAL`, `NEGATIVE`, `FRUSTRATED`, `MIXED` |
| `severity` | enum | No | — | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `status` | enum | No | — | `NEW`, `INVESTIGATING`, `RESOLVED`, `CLOSED` |
| `from` | ISO date | No | — | Inclusive start date, for example `2026-08-01` |
| `to` | ISO date | No | — | Inclusive end date, for example `2026-08-31` |
| `search` | string | No | — | Case-insensitive search across issue summary and original feedback; maximum 200 characters |
| `project_id` | string | No | — | Project filter; must be permitted by the dashboard API key |
| `sort` | enum | No | `newest` | `newest`, `oldest`, or `severity` |
| `page` | integer | No | `1` | Minimum `1` |
| `pageSize` | integer | No | `25` | Range `1`–`100` |

Example:

```http
GET /api/issues?severity=CRITICAL&status=INVESTIGATING&sort=newest&page=1&pageSize=25
```

### Success response

**Status:** `200 OK`

```json
{
  "items": [
    {
      "id": "ISS-1001",
      "summary": "Generated application fails during build",
      "originalFeedback": "The generated app looks correct, but the build fails with a module resolution error.",
      "aiSummary": "Generated project cannot resolve a dependency during production build.",
      "category": "BUILD_FAILURE",
      "subcategory": "Module resolution",
      "sentiment": "FRUSTRATED",
      "severity": "CRITICAL",
      "aiConfidence": 0.96,
      "status": "INVESTIGATING",
      "createdAt": "2026-08-12T14:30:00.000Z",
      "userReference": "user_2048",
      "projectReference": "project_alpha",
      "conversationId": "conversation_9001",
      "metadata": {
        "browser": "Chrome 126",
        "environment": "production"
      }
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 25,
    "total": 1,
    "totalPages": 1
  }
}
```

### Validation error

**Status:** `400 Bad Request`

```json
{
  "error": "Validation failed",
  "details": {
    "fieldErrors": {
      "severity": ["Invalid option: expected one of ..."]
    },
    "formErrors": []
  }
}
```

## 3. Get Issue Details

### `GET /api/issues/:id`

Returns a single issue and its available detail metadata.

Example:

```http
GET /api/issues/ISS-1001
```

### Success response

**Status:** `200 OK`

The response is one issue object with the same fields described in the list response, including original feedback, AI summary, AI confidence, references, timestamps, and metadata.

### Not found response

**Status:** `404 Not Found`

```json
{
  "error": "Issue not found"
}
```

## 4. Update Issue Status

### `PATCH /api/issues/:id`

Updates the workflow status of an issue. This endpoint requires a dashboard API key with access to the issue's project.

Headers:

```http
Content-Type: application/json
x-api-key: <dashboard-api-key>
```

Request body:

```json
{
  "status": "CLOSED"
}
```

Allowed statuses:

```text
NEW
INVESTIGATING
RESOLVED
CLOSED
```

A successful update returns the updated issue object with status `200 OK`.

To close an issue specifically:

```http
PATCH /api/issues/<feedback_id>
```

```json
{
  "status": "CLOSED"
}
```

Possible errors are `400 invalid_json`, `401 invalid_dashboard_api_key`, `404 issue_not_found`, and `422 validation_failed`.

## 5. Deprecated Feedback Aliases

These endpoints are retained for compatibility with earlier frontend integration work. New consumers should use `/api/issues`.

### `GET /api/feedback`

Read-only alias for `GET /api/issues`. It accepts the same query parameters and returns the same response shape.

### `GET /api/feedback/:id`

Read-only alias for `GET /api/issues/:id`.

The previous feedback ingestion, update, and delete methods are intentionally not exposed on these routes.

## 6. Deprecated Dashboard Summary

### `GET /api/dashboard/summary`

This endpoint is no longer part of the issue-list module.

**Status:** `410 Gone`

```json
{
  "error": "Dashboard summary is not part of the issue-list module. Use /api/issues."
}
```

## Common integration example

```ts
const response = await fetch('https://api.example.com/api/v1/feedback', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'x-api-key': process.env.FEEDBACK_API_KEY!,
    'Idempotency-Key': crypto.randomUUID(),
    'X-Request-ID': crypto.randomUUID(),
  },
  body: JSON.stringify({
    message: 'The application generated by AI is failing to build.',
    user_id: 'user_123',
    conversation_id: 'conv_456',
    project_id: 'project_789',
    source: 'ai-builder',
    page_url: '/projects/123',
    metadata: {
      request_id: 'req_123',
      environment: 'production',
    },
  }),
});

if (!response.ok) {
  const error = await response.json();
  throw new Error(`${error.error.code}: ${error.error.message}`);
}

const acknowledgement = await response.json();
```

## Contract notes

- This document reflects the current route handlers and validation schemas.
- The ingestion endpoint is persistence-backed through Prisma.
- The issue list and status updates are persistence-backed through Prisma.
- Issue routes require dashboard authentication and project-scoped access.
